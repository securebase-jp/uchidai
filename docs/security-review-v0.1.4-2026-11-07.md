## 見つけた問題

### PS-001（低）貼り付けの URL と `sourceUrl` は、`http(s)` 以外のスキームも通る

`pastes[].url`（`apps/web/src/shared/api.ts`）と、`kind: "text"`／`"pdf"` の `sourceUrl` は `z.string().url()` だけで、スキームを見ません（`new URL()` が読めれば `javascript:`、`file:`、`data:` も通ります）。`kind: "urls"` の `urls` も同じ形ですが、こちらは取得の前に `assertPublicUrl` が `http(s)` 以外を断ります。**貼り付けのある URL は取得に行かないので、この検査を通りません**（新しく増えた経路）。通った値は、応答の `series.parts[].url`、`article.sourceUrl`、`wrapArticle` の `source=` 属性（エスケープされる）、画面の `caseMeta.sourceUrl`、localStorage に入ります。

- 悪用できるか：**いまは悪用できません。** 画面は URL を `<code>{f.url}</code>` の文字として出すだけで、`href` には使いません（`apps/web/src/client` の `href=` を全部確かめました。`KevPanel` は KEV の固定の取得元、`Sources` は知識ファイルの URL）。取得にも行きません（試験 `PS（Issue #6）貼り付けの扱い`）。自分で `javascript:` の URL を入力する人は自分自身にしか影響しません。
- 残る危険：今後、報の URL をリンクにする変更が入ったとき、`javascript:` がそのままリンクになります。入力の形を 1 か所で締めるほうが、描画のたびに気を付けるより確実です。
- 推奨：`pastes[].url`、`sourceUrl`、ついでに `urls` の各要素を `http:` と `https:` だけにする（zod の `refine`、または `z.url({ protocol: /^https?$/ })`）。
- 試験：`v014.security.test.ts` の `PS-001`（現状を `it`、望ましい振る舞いを `it.fails`）。

### DL-001（低）取引先への通知の期限が、一枚では「契約で定められた期限」の 0 日目として出る

`knowledge/deadlines.yaml` の `partner-notice-breach`（情報漏えい、`days: 0`、`status: unverified`）。時間軸（`timeline`）の詳細には「日数は契約ごとに異なり、法令にはない（要確認）」が付きますが、**社長向けの一枚の期限（`OnePagerDeadline`）は `labelJa`・`day`・`sourceJa` しか持たない**ので、一枚には「0 日目　取引先への通知（契約で定められた期限）」とだけ出ます。出典の欄は「会社カルテ（サイバー保険の契約、取引先との契約）」です。

- 事実と合わない点：(1) 0 日は契約の期限ではなく「契約の確認を始める目安」（`noteJa` に書いてあるが一枚に出ない）。(2) 出典が「会社カルテ」なので、カルテに取引先との契約の通知条項が登録されているように読める（実際は何も読んでいない）。(3) `damage_type` の期限なので、取引先から情報を預かっていない会社でも、`data_breach` なら必ず出る。同じ 0 日に置く警察の期限は見出しに「（目安）」が付くが、この期限の見出しには何も付かない。
- 影響：誤って安心させる方向ではなく、期限があるかのように見せる方向のずれです。経営者が「契約の期限は当日」と受け取るおそれがあります。
- 推奨：見出しを「取引先への通知（契約で定められた期限。日数は契約で確認）」のようにするか、`timeline.ts` の `damage_type` の分岐で、`unverified` なら `（要確認）` を `labelJa` に付ける（一枚が読むのは `labelJa` だけで、`detailJa` に付けても一枚には出ない）。出典の欄は「会社カルテ」ではなく「契約書（要確認）」にする。
- 試験：`packages/engine/src/v014.security.test.ts` の `DL-001`（`it.fails`）。

### LG-001（低・既存）ログの URL の伏せ漏れ（`redactUrls`）

`UCHIDAI_LOG_REDACT_URLS=1` のとき、ログの URL のパスとクエリが伏せられます。正規表現 `[^\s'"<>)\]]*` が次の文字で止まるため、**そのあとのパス・クエリが残ります**（試験で確かめました）。

| 入力（架空）                                            | 出力                                                             |
| ------------------------------------------------------- | ---------------------------------------------------------------- |
| `https://h.example/wiki/A_(b)?token=SECRET`             | `https://h.example/[省略])?token=SECRET`（`)` から後ろが残る）   |
| `http://[2001:db8::1]:8080/p?token=SECRET`              | 変わらない（ホストの `]` で止まり、全体が URL として扱われない） |
| `https://h.example/a'b?token=SECRET`、`…/a"?t=…`        | 引用符から後ろが残る                                             |
| `www.example.com/secret?token=…`、`//cdn.example/x?k=…` | 伏せない（スキームなし、`//` から始まるもの）                    |

- 影響：ログは同じ PC の標準エラーに出るだけで、外へは出ません。ただし、この機能の目的は「ログに記事の URL（取引先名や案件名を含むパス）を残さない」ことなので、`)` を含む URL や IPv6 の URL で意図が果たせません。既定は無効なので、既存の利用には影響しません。
- 推奨：URL の末尾の判定を「空白、引用符、`<>` まで」に変える（`)` で止めない。`)` や `]` の扱いは、URL の直前に `(` や `[` があるときだけ末尾から外す）。IPv6 のホスト（`[...]`）を許す。スキームなしの `www.`・`//host` は、伏せるかどうかを決める。
- 試験：`v014.security.test.ts` の `LG-001`（`it.fails` が 2 本）。

### LG-002（情報・既存）`redactUrls` が、長い入力で長さの 2 乗の時間になる

`/\b([a-z][a-z0-9+.-]*):\/\/…/gi` は、`://` が無い長い「`a.a.a.…`」のような文字列で、開始位置ごとに末尾まで走査して戻ります。測定（この PC）：`"a.".repeat(10_000)`（2 万字）で約 0.3 秒、`"a.".repeat(50_000)`（10 万字）で約 8 秒（長さの 2 乗）。

- 悪用できるか：`redactUrls` に渡るのは、500 の例外の `stack`・`message`・`cause`（3 段まで）で、**攻撃者が長さを選べる文字列は見つけられませんでした**（記事の本文は例外のメッセージに入らず、URL は 2048 字まで）。`UCHIDAI_LOG_REDACT_URLS=1` のときだけ動く。推測にとどまるため情報とします。
- 推奨：`[a-z0-9+.-]*` を `{0,30}` のように上限つきにする（スキームの名前は短い）。
- 試験：`LG-002`（`it.fails`、3 万字で 100 ms 以内）。

### SR-001（情報・既存）系列の各報の読解の失敗が、整形せずに応答へ出る

`apps/web/src/server/series-read.ts` の `readErrors[].message` は `e.message` をそのまま返します（他の経路は `publicMessage` を通す）。例外の文にサーバのパスや環境変数の値が入っていれば、画面に出ます（試験で再現：偽の例外 `…/Users/someone/work/key.json ANTHROPIC_API_KEY=abc123xyz`）。

- 悪用できるか：`readCase` が投げる例外の文は、Anthropic SDK のエラーと検証の文で、パスや環境変数の値は通常含みません。手元専用で、応答を読むのも同じ利用者です。実害の根拠は薄く情報とします。
- 推奨：`publicMessage(e)` を通す（1 行）。
- 試験：`SR-001`（`it.fails`）。

### WR-001（情報・既存）記事の囲いの無害化は、見えない文字をはさんだ閉じタグを通す

`wrapArticle` は `<` の直後が `\s*article` や `\s*/\s*article` のときだけ `&lt;` にします。`<` と `article` の間にゼロ幅スペース（U+200B）などを置いた `<​/article>` や、全角の `＜/article＞` は、そのまま本文に残ります（出力を確かめました）。

- 悪用できるか：モデルがこれを囲いの終わりとして扱うとは限りません（記事の本文は user ターンで、システムの指示とは分かれている）。**記事の囲いを実際に破った例は作れていません**。推測にとどまり情報とします。貼り付けの本文も同じ経路です（Issue #6 で増えた経路ではなく、`kind: "text"` と同じ）。
- 推奨：`<` のあとの不可視文字（U+200B〜U+200D、U+2060、U+FEFF）を無視して照合する、または、本文に残った `<` ＋ 英字 `article` の近傍の不可視文字を取り除く。
- 試験：`WR-001`（`it.fails`）。

### PO-001（情報）「取引先・提供元の停止」は、記事の分類だけで、報告義務の期限を消し、「御社は侵入されていません」と言い切る

型紙 `partner-outage` と被害の種類 `partner_outage` は、`reportsPersonalData: false`（個人情報の報告・本人通知の期限を出さない）と、`noEntry`（入口なしのとき「御社は侵入されていません。…業務は止まりません」）を持ちます。**被害の種類は Claude が記事から読む値**で、記事の本文（信頼できないデータ）で左右されます。

- 設計の芯は崩れていません：判定（止まる業務、日数、期限）はプログラムで、`partner_outage` を選ぶ経路は従来の被害の種類と同じ仕組みです（記事を分類し、型紙が決まる）。`partner-outage` の判定ルールは `breached` だけで、「止められる」は出せません（試験）。カルテが初期の枠のままなら、入口なしは出さず `pending` に倒します（`evaluate.ts`）。
- 新しくなった点：記事が「取引先の被害で停止した」と書き、読解がそう分類すると、(1) 個人データの報告の期限が出ない、(2) 依存が登録されていないカルテでは「御社は侵入されていません」が**事実として**見出しに出る（試験 `PO-001`）。実際には記事の分類が間違い（または記事側が誘導）でも、見出しには出所（「この記事の分類では」）が出ません。
- 推奨（v0.1.4 の後でよい）：見出しを「この記事の事故は、取引先・提供元の停止と読めます。御社が侵入されたものではありません」のように記事の読みに紐づける。画面の「Claude が読んだ被害の種類」と並べて、利用者が分類を直せるようにする（すでに事例の種類は直せるなら、そこへ誘導する）。
- 試験：`PO-001`（現状を `it` で固定）。

### RD-001（情報）読解の指示への追加（記載されたリスト型ログインを入口に置く）

`packages/llm/src/prompts.ts` の追加は、システムの指示（信頼できる側）に静的に書かれた 1 項目で、記事の本文は引き続き `wrapArticle` の中です。**記事を指示として扱う余地は増えていません。**

- 見るべき点：この項目は「記事に〜と書かれているとき入口の段階に置く」という条件つきの指示なので、記事の本文でその条件を満たす（「リスト型攻撃で不正ログインされた」と書く）ことが、入口の段階を作る入力になります。入口の種類（`credential`、`service-account`）は、判定では `pinsAsset` で資産に当てるだけで、「止められる」へ直接つながる経路はありません（サービスアカウントの判定ルールに `blocked` は無い）。記事の本文で左右される範囲は、以前の「入口の種類」と同じ水準です。
- 推奨：なし（記録のみ）。評価（`pnpm eval:articles`）で、リスト型と詐称の記事が追加の項目に釣られないか見続けるのがよいです。

### DOC-001（情報）`SECURITY.md` の対象バージョンが古い

`SECURITY.md` の「対象バージョン」が「リリース番号はまだ無い」「`main` の最新だけ」のままです（v0.1.0 以降、タグつきで公開済み）。報告者が、どの版が修正の対象か分かりません。公開の前に更新を勧めます。

## 確かめて問題なかったもの

### 1. 失敗した取得の取り直しと貼り付け（Issue #6）

- **貼った URL へは取得に行かない**：`pastes` のある URL は `kind: "text"` で読み、`kind: "url"` は呼ばれない。内部アドレス（`http://169.254.169.254/…`）の URL を貼り付けで差し替えても、取得は一切起きない。
- **`pastes` の URL が `urls` に無いとき**：使われない（取得にも行かない）。`urls` と表記がずれた貼り付け（大文字小文字、末尾のスラッシュ）は照合されず、`urls` 側が従来どおり SSRF の検査つきで取得される。取得先が増えることはない。
- **貼った本文が空白だけ（40 字以上）**：取得にフォールバックせず、`empty` の失敗として返る。
- **記事の囲い**：貼った本文の `</article>`、`< /ARTICLE >`、`<article source=…>` は `&lt;` に直る。`source` と `title` の属性のエスケープ（引用符、`<>`、制御文字）も保たれる。
- **サイズ・件数の上限**：`pastes` は 5 件まで、各 40 字以上 30 万字まで（zod）。リクエスト全体は読解の上限（約 7 MB）で 413。連結後の本文は `MAX_SERIES_CHARS`（15 万字）で 422。各報は 10 万字で切る。5 件 × 30 万字が来ても、メモリの使い方は `kind: "text"` の 5 倍までで、Claude の呼び出しは増えない（読解の回数の上限は 1 リクエスト 1 回と数える設計のまま）。
- **情報漏えい**：`reason` は取得の失敗の種類（`forbidden`／`not_found`／`empty`／`thin`／`bad_pdf`／`other`）だけで、判定には使われない。内部アドレスの URL は取得の前に断られるので、`reason` は常に `other`（内部ホストの応答の有無を推し量れない）。応答にパス・スタック・キーは出ない（試験）。
- **画面**：URL・理由・メッセージは React の文字として出し、`href` にしない。`dangerouslySetInnerHTML`・`innerHTML`・`outerHTML`・`insertAdjacentHTML`・`document.write` は `apps/web/src` の画面側にもサーバ側にも無い（試験で数えている）。`fetchFailures` は localStorage に保存するが、`looseObject` で形だけ検査し、文字として出す。

### 2. ログとデモ API（Issue #1、既存）

- `redactUrls`：ユーザー情報、パス、クエリ、フラグメントを伏せる（大文字のスキームも）。`cause` の連鎖は 3 段で止まり、循環しても終わる（試験）。伏せ漏れは LG-001、時間は LG-002。
- `routes/demo.ts`：`NODE_ENV=production` で `UCHIDAI_DEMO_AUDIO` が `1` でなければ `/api/demo/*` は全部 404。場面番号は整数 1〜50 に限り、ファイル名に入るのは数字だけ（パスの走査なし）。`NODE_ENV` が未設定でも、配るのは `demo/audio/*.wav`（git 管理外）だけで、無ければ空。
- `Dockerfile` は `NODE_ENV=production` を設定。`scripts/portable/launcher.mjs` も `production` にする。`docker-compose.yml` は上書きしない（`read_only: true`）。いずれも `v0.1.3..main` で変更なし。

### 3. 共有リンクの差分と一枚の段組み（Issue #11、#12）

- 共有リンクの差分は `resultWordJa`（300 字まで、文字列のみ）の 1 項目。長さの上限、オブジェクトの拒否を試験で確かめた。タグ状の文字列（`<img onerror=…>`）は上限内ならただの文字列として通るが、描画は React の文字（`<b className="op-word">{…}</b>`）で、HTML として解釈されない。
- 既存の上限は保たれている：`d=` は 64 KB、展開後は 1 MB（展開しながら数えて打ち切る）、文字列 300／2,000 字、配列 50 件、`changesJa` は 2 文まで。
- `fit.ts`・`sheet-layout.ts`・`exportPdf.ts`：DOM への書き込みは、`data-fit-a`／`data-fit-b`（0〜3 の数字）の属性と、既存の節の `cloneNode` だけ。記事・共有リンク由来の文字列を HTML として挿入しない。段の探索は最大でも a・b で 3 段ずつ（高々 7 回の測定）で終わり、無限ループにならない。測定用の入れ物は画面の外に置き、`finally` で必ず外す。

### 4. 依存の整理（Issue #9）

- `apps/web/package.json` と `pnpm-lock.yaml` の差分は、`@fontsource/*`、`html-to-image`、`jspdf`、`lucide-react`、`motion`、`react`、`react-dom` を `dependencies` から `devDependencies` へ**移しただけ**。**バージョンの変更も、新しい依存の追加もありません**（ロックファイルの `specifier`／`version` は同じ）。
- サーバと共有コード（`apps/web/src/server`、`apps/web/src/shared`、`packages/*/src`）は、移した依存を 1 つも import しない（grep で確認）。本番イメージの `pnpm install --prod` と、ZIP の `collectRuntimePackages`（サーバが import するものだけを集める）から欠けるものはない。
- 逆に、本番の依存の閉包から `react`、`jspdf`（とその依存）などの画面用のパッケージが外れ、攻撃面は減った。

### 5. 知識の追加と判定の変更（Issue #7・#8）

- 判定はプログラムのまま：新しい型紙 `partner-outage`、`service-account-takeover` の判定ルールは、`knowledge/rules/` の YAML が決める。Claude が決めるのは記事の読み（段階、手法、入口の種類、被害の種類）まで。サービスアカウントの判定ルールに `blocked`（止められる）の結果は無く、最良でも `recoverable`（漏れても気づいて失効できる）。取引先・提供元の停止は `breached` だけ（試験）。
- 同数の型紙が並ぶときの入口候補（`evaluate.ts`）：共通の入口だけを残し、共通が無ければ `pending`「入口はまだ分かっていません」に倒す。以前の「全部の入口を出す」より、誤った断定は減る方向の変更。
- `fromPartner` の入口は、`side: "external"` で、止まる業務（`recoveryDays > 0`）が頼る資産だけ。攻撃者とのつながりは要らないが、カルテの外の資産は当たらない。`isDecommissioned` の除外も効く。AI 攻撃者の手法の表（`attacker.ts`）には混ざらない（`fromPartner` を除く）。
- 期限の追加（`partner-notice-breach`）：`unverified` の表示は時間軸には出る。一枚で出ない点は DL-001。
- 質問の追加（`UD-10`、`UD-11`）：固定の文面で、カルテ由来の文字列を含まない。選択肢は `present`／`absent`／`unknown` だけ。まとめて確認の文面の無害化（AR-001/002）に影響しない。
- 知識ファイル：`labels.ja.yaml`、`costs.yaml`、`measures.yaml`、スキーマに、実行されるコードや外部の URL は無い。`eval/trials/articles/supply-oos.yaml` は URL と要約だけで、記事の本文は入っていない。

### 6. 以前の診断の対応済み項目（退行なし）

- `app.ts` の守りの順序（CORS → `remoteGuard` → `hostGuard` → `sameOriginGuard`（SSE の GET を含む）→ 本文の上限）は変わらず、`/api/case/read` の新しい形（`pastes`）も同じ手前の検査を通る。
- SSRF：`loadArticle` の `kind: "url"` は、`assertPublicUrl` ＋ `guardedFetch(pinningFetch())`（IP の固定）のまま。`kind: "text"`・`"pdf"` は取得しない。貼り付けは取得を避けるだけで、検査を弱めない。
- 読解の回数の上限（`takeClaudeSlot("read")`）、記事取得の同時数、本文の上限（5 MB、PDF）、まとめて確認の送信の上限・無害化・`expectText`（AR-001/002、BK-001）に、今回の差分は触れていない。それぞれの既存の試験は通る。

### 対応の内容（PS-001、DL-001、LG-001/002、SR-001、DOC-001）

- **PS-001**：`apps/web/src/shared/api.ts` に `isHttpProtocol` と `HttpUrl` を置き、`url`、`urls`、`pastes[].url`、`sourceUrl`（本文・PDF）をすべて `http(s)` に限った。取得経路の確認（`safe-url.ts` の `checkPublicUrl`）も同じ `isHttpProtocol` を使う（取得側の判定は緩めていない）。
- **DL-001**：`timeline.ts` の `damage_type` の分岐で、`unverified` の期限の `labelJa` に「（要確認）」を付け、出典が会社カルテのものは「契約書（要確認）」にした。確定している期限（警察、送金の組み戻し）は変わらない。
- **LG-001/LG-002**：`redactUrls` を、スキームつき（IPv6 の `[...]` を含む）、`//` で始まるもの、`www.` で始まるものの 3 回の走査にした。パスの `)` と引用符で止めず、URL のあとの句読点・閉じ括弧・引用符だけを残す。スキーム名に長さの上限（30 字）を付け、長い入力でも線形。スキームも `//` も `www.` も無い `example.com/x` のような形は、ファイル名や文との区別がつかないため伏せない。
- **SR-001**：`series-read.ts` の `readErrors[].message` を `publicMessage` に通した。
- **DOC-001**：`SECURITY.md` の対象を「最新のリリース（と `main` の最新）」にした。版が変わっても書き換えは要らない。

## 診断の範囲外・確認できなかったこと

- 実在サイトへの取得、Claude の実際の応答（読解・言い換え）は動かしていません。「記事の本文で入口・期限・型紙の選択を操作できるか」は、プログラム側（記事の読みが与えられたときの判定）を試験で確かめ、モデルがどこまで誘導されるかは確かめていません。これは `pnpm eval:articles`（記録の再生）の範囲です。
- 画面の描画（DOM）は実行していません。XSS の有無は、コードの読解（HTML を書き込む API が無いこと）と、入力の検査の試験で見ています。
- `portable:build`／`portable:smoke`（ZIP の実機の起動）は動かしていません。ZIP と Docker が移した依存を要らないことは、import の grep とビルド手順（`collectRuntimePackages`、`pnpm install --prod`）の読解で確かめました。
- 依存の既知の脆弱性：バージョンの変更が無いため、今回は調べていません（`v0.1.3` から変わっていない）。
