# セキュリティ診断：ベンダーへの「まとめて確認」の設計（2026-11-07）

対象：(A) 現在の確認依頼の実装（コミット `6f6f49e`。`apps/web/src/shared/requests.ts`、`server/routes/requests.ts`、`server/store/requests.ts`、`server/requests/questions.ts`、`server/mail/mailer.ts`、`packages/llm/src/writer.ts`、`client/components/{RequestPanel,OutboxPanel}.tsx`、`client/hooks/useRequests.tsx`、`client/lib/requestsApi.ts`）と、(B) これから実装する「選んだ N 件（最大 10 問）を同じ宛先へ 1 通のメールにまとめて送る」設計です。実装の前に行う診断なので、(B) はコードではなく PM の設計案を読んで評価しています。コードは変えていません。

確かめた方法：コードの読解と、手元の `app.request` による単体試験（`apps/web/src/server/routes/requests-batch.security.test.ts`。外へ出る通信はしません。Claude は呼ばず、書き手はテンプレートに固定しています）。2026-11-06 の診断（`docs/security-review-2026-11-06.md`）と CodeQL の仕分け（`docs/codeql-triage-2026-11-06.md`）で対応済みの項目（CSRF、Host、宛先の形、Claude の回数の上限、`mailto:` の符号化、SMTP のヘッダ注入）は重複して書かず、残っている穴と、新機能が増やす攻撃面に絞っています。「確かめたこと」と「コードを読んだ限りの推定」は分けて書きます。

## 結論

- 現在の実装の芯（宛先は 1 件のメールアドレスの形だけ、`mailto:` と SMTP の注入は符号化と nodemailer が防ぐ、Claude の下書きは検証して落ちればテンプレート、保存は一時ファイルから `rename`、回答は依頼に保存された `choiceMap` からしか選べない）は保たれています。重大度「高」はありません。
- 現在の実装で見つけた問題は 8 件（中 1、低 5、情報 2）です。急ぐのは **BR-001（保存の上限を同時の要求がすり抜ける）** と **BR-003（`mailto:` が 1 問でも約 3,800 字あり、メールソフトによっては本文が切れる）** で、どちらも、まとめ依頼で影響が大きくなります（子の件数ぶん上限を超える、10 問で約 12,800 字）。
- 設計で実装前に決めるべきことは 5 件です：(1) 返信の反映は「全件を検証してから全件を適用する」（原子性）、(2) 取り消しは質問ごとと親ごとの両方を定義し、親の取り消しは子の全取り消しにする、(3) `mailto:` に頼らず「本文をコピー」と `.eml` の書き出しを主な送り方にする、(4) まとめのメールには手法 ID と「判定の材料」を載せず、宛先が無ければ作らせない、(5) 件数の上限は「重複を除いた後の件数」と「保存の空き（親 1 ＋ 子 N）」の両方で見て、1 回の原子的な保存にする。
- まとめ依頼は Claude を呼ばないので、SEC-006 の回数の上限（`takeClaudeSlot`）の外に出ます。SMTP を設定している環境では「1 分に送れる通数」の上限を別に設けてください（SBR-012）。

### 信頼境界

1. **ブラウザ → サーバ**：`ProfileExcerpt` は zod で形を見るが、内容（資産名など）は信用しない前提で扱うべきもの。まとめ依頼でも同じ抜粋を受ける。
2. **サーバ → `.data/requests.json`**：サーバだけが書く。読むときは `StoredShape`（looseObject）で最低限の形だけ見る。`answer` と `profileId` は検証されない。
3. **サーバ → SMTP／`mailto:`**：件名・本文・宛先が外に出る境界。宛先は 1 件のアドレスの形に固定済み（SEC-007）。本文の内容（弱点の候補）は、まとめ依頼で密度が上がる。
4. **サーバ → 画面（SSE と JSON）**：回答の反映は画面の `addAnswer` → `/api/evaluate`。`AnswerInput` は `/api/evaluate` 側で zod 検証される。

## 実装前に決めるべきこと（設計の変更案）

優先度の順です。

1. **返信の反映は原子的にする（SBR-004）**。`store.recordReply` は 1 件ずつ検証して保存するので、配列をそのまま回すと「3 問目で落ちたとき 1〜2 問目だけ反映される」状態になります。先に全件を検証（子が親のもの、未回答、選択肢が `choiceMap` にある、日時が読める）してから、1 回の `persist()` で全件を書き、SSE は反映した件数ぶん流す、の順にしてください。一部だけの回答（未入力の質問は残す）は「入力した質問の集合に対して全件成功か、全件失敗か」の意味で原子的にします。
2. **取り消しの意味を決める（SBR-006）**。質問ごとの取り消し（子の `retract`）と、親の取り消し（子の全取り消し）の両方を API に置くか、質問ごとだけにするか。親を消す操作（送信箱を空にする `DELETE /`）は、子も一緒に消すこと（親だけ消えて子が孤児になると、画面が「依頼済み」と誤って見せ続けます）。
3. **`mailto:` を主な送り方にしない（SBR-010、BR-003）**。1 問でも `mailto:` は約 3,800 字で、10 問では約 12,800 字です。メールソフトや OS によって、長い `mailto:` の本文を切る、または開かない実装があります（具体的な上限は実装ごとに異なり、この診断では実機で確かめていません）。まとめ依頼では「本文をコピー」と `.eml`（または `.txt`）の書き出しを主にし、`mailto:` は短い場合の補助にしてください。切れた本文で質問が欠けると、ベンダーの回答と担当者の入力の対応がずれ、判定が誤ります。
4. **まとめのメールの情報量を減らす（SBR-011）**。1 問の依頼では「攻撃の手法 ID」「判定の材料」「対策 ID」を背景として載せていますが、10 問並ぶと「どの資産にどの攻撃が通りそうか」の一覧になります。まとめでは、質問ごとに資産名と質問文と選択肢だけにし、背景は「報道された攻撃への備えの確認」の 1 文にまとめることを勧めます。あわせて、宛先が無いときは作らせない（400）、プレビューで宛先を目立たせる、送信箱に積む前に「この宛先でよいか」を確認する、を画面の要件にしてください。
5. **件数と保存の上限を 1 か所で数える（SBR-007、BR-001）**。`items` は `(assetId, mitigation)` で重複を除いてから数え、重複を除いた後に 1〜10 件。保存は `store.size + 1 + N <= maxRequests` を、親と子を 1 回の `add` で積む直前（`await` の後）に見てください。いまの `POST /` は `await writeVendorRequest` と `await mailer.send` の前に `store.size` を見るので、同時の要求がすり抜けます（BR-001 で確認済み）。
6. **子の依頼の識別**。子は `id` を別に持ち、`parentId` で親を指す。`POST /:id/reply` に子の `id` を渡したときの挙動（許す／`batch` の経路に誘導して 409）を決め、`POST /batch/:id/reply` に子や 1 問の依頼の `id` を渡したら 404 にしてください。
7. **番号の振り方の一元化（SBR-008）**。質問ごとに 1 から振り直す（「■ 質問 1」の中で 1・2・3）のは、いまの `numberedChoices` の約束（質問表の並び順で 1 始まり）と同じで、送信箱の入力欄もその並びを使えます。通し番号（1〜30）にすると `numberedChoices` の約束が崩れるので採らないでください。
8. **保存の形の版**。`requests.json` の `version` を 2 に上げ、親は `kind: "batch"`、子は `parentId` を持つ。読み込みでは、`parentId` が指す親が無い子、子を持たない親、親と `profileId`・`to` が違う子は捨てる（または親から補う）。古い版（親子の無い項目）はそのまま読めます。

## 現在の実装で見つけた問題（BR）

重大度は SBR と同じ基準です。いずれも、手元の `app.request` の単体試験で再現しています（「確認済み」）。試験は `requests-batch.security.test.ts` の「BR」の節にあり、直したら期待値を反転してください。

### BR-001（中）保存の上限（`maxRequests`）を、同時の要求がすり抜ける

- 該当：`apps/web/src/server/routes/requests.ts:122-126`（`store.size` の確認）、`:136`・`:157`（そのあとの `await writeVendorRequest` と `await mailer.send`）、`:183`（`store.add`）
- 何が起きるか：上限の確認が `await` の前にあるので、確認と `add` の間に別の要求が割り込みます。`maxRequests: 1` で、送信に 30ms かかる Mailer を使い 3 本を同時に送ると、3 本とも 201 で `store.size` は 3 になりました（確認済み）。Claude を呼ぶ書き手では `takeClaudeSlot` が 1 分 20 回で間接的に抑えますが、テンプレートの書き手と、Claude を呼ばないまとめ依頼では抑えが無く、まとめ依頼は 1 本で 11 件積むので、上限の意味が薄れます。
- 悪用の条件：手元の画面（または画面の自動操作）だけ。他サイトからは SEC-002 で止まります。影響は保存の件数とファイルの大きさ（`requests.json` を毎回 JSON 全体で書き直すので、件数が増えるほど 1 回の保存が重くなる）です。
- 直し方の案：`store.add` の直前（`await` の後）でもう一度 `store.size` を見るか、`RequestStore.add` に上限を持たせて超えたら例外にし、経路で 429 に写す。まとめでは `store.addMany(parent, children)` を 1 回の `persist` にし、その中で `size + items.length <= max` を見る。
- 規模：小。

### BR-002（低）`fillNames` のプレースホルダの置換が連鎖し、カルテ由来の文字列が別の名前に化ける

- 該当：`packages/llm/src/writer.ts:80-93`
- 何が起きるか：置換は `{{company}}` → `{{vendor}}` → `{{asset}}` → `{{staff}}` の順に、文全体へ `replaceAll` を重ねます。会社名に `{{asset}}` が入っていると、次の段で資産名に化けます。資産名に `{{staff}}` が入っていると「情報システム担当」に化けます（確認済み：会社名 `{{asset}}社`、ベンダー名 `{{staff}}`、資産名 `{{company}}` で、出力は `{{company}}社 / 情報システム担当 / {{company}} / 情報システム担当`）。逆に、後ろの段で差し込まれた `{{company}}` は置換されずに残ります。`validateVendorDraft` は Claude の下書きの中の未知のプレースホルダを見ますが、差し込む名前の側は見ていません。
- 悪用の条件：カルテの会社名・資産名・ベンダー名に `{{...}}` を書く（悪意あるカルテやバックアップの JSON を読み込ませる）。影響はメールの文面の名前が変わることで、宛先やヘッダには届きません（宛先は別の経路で、形を検証しています）。
- 直し方の案：差し込む前に名前の中の `{{` と `}}` を全角などに置き換える。または 1 回の正規表現 `/\{\{(company|vendor|asset|staff)\}\}/g` で、関数置換により同時に差し込む（連鎖しない）。
- 規模：小（10 行）。

### BR-003（低）`mailto:` が 1 問でも約 3,800 字。まとめ依頼では 10 問で約 12,800 字

- 該当：`apps/web/src/server/mail/mailer.ts:23-30`、`client/components/OutboxPanel.tsx:176`（主な送り方が `mailto:` のリンク）
- 何が起きるか：日本語は 1 字が 9 字（`%E3%81%82`）に膨らみます。M1026 の 1 問で本文 450 字、`mailto:` は 3,787 字でした（確認済み）。テンプレートの質問の塊を 10 個に増やした概算で、本文 1,728 字、`mailto:` は 12,760 字です。`mailto:` の長さの扱いはメールソフトと OS で異なり、長い本文を切る、または開かない実装があります（具体的な上限はこの診断では実機で確かめていません。推定）。質問が末尾から欠けると、ベンダーは残った質問にだけ答え、担当者は送信箱の質問の並びで番号を入力するので、**番号と質問の対応がずれて判定が誤る**経路になります。
- 直し方の案：送信箱に「本文をコピー」（`navigator.clipboard.writeText`）と「メールの下書きを保存」（`.eml` を `text/plain` の本文で組み、`Content-Transfer-Encoding: base64` で書き出す。`nodemailer` の `streamTransport` で作れる）を置き、`mailto:` は補助にする。まとめ依頼では必ずこの形にする（SBR-010）。
- 規模：小〜中（画面 1 か所と、`.eml` の生成）。

### BR-004（低）カルテ由来の文字列の制御文字が、件名・本文・画面に素のまま入る

- 該当：`apps/web/src/shared/requests.ts:78-87`（`ProfileExcerpt` は長さだけ）、`routes/requests.ts:136-152`（そのまま `writeVendorRequest` へ）
- 何が起きるか：会社名 `A\r\nBcc: x@example.com`、資産名 `管理者‮\u0000アカウント` を渡すと、件名は `【ご確認のお願い】管理者<U+202E><NUL>アカウントの…について（A\r\nBcc: x@example.com）` になりました（確認済み）。SMTP のヘッダ注入にはなりません（nodemailer 10 が CR LF を畳むことは前回の診断で確認済み）し、`mailto:` は符号化されます。しかし、NUL と双方向制御文字（U+202E は以後の文字を右から左に見せる）は件名・本文・送信箱のプレビューにそのまま残り、プレビューで宛先や資産名の見え方を変えられます。まとめ依頼では「プレビューで宛先と文面を確認する」ことが誤送信の最後の守りなので、見え方を変えられる文字は取り除くべきです。
- 直し方の案：`ProfileExcerpt` の各文字列に `.transform` で制御文字と双方向制御文字を取り除く（または `.refine` で 400）。SBR-013 と同じ関数を 1 問の依頼にも使う。
- 規模：小。

### BR-005（低）保存ファイルの `answer` を読み込み時に検証していない

- 該当：`apps/web/src/server/store/requests.ts:53-71`（`StoredShape` に `answer` が無く、looseObject で素通し）、`client/hooks/useRequests.tsx:66-77`（起動時に `it.answer.input` を `addAnswer`）
- 何が起きるか：`requests.json` の項目に `answer: { choice: "zzz", input: { assetId: "OTHER", mitigation: "M9999", status: "absent", evidence: "external", … } }` を書くと、そのまま読み込まれ（確認済み）、画面は起動時にこの `input` を判定の回答として適用します。`/api/evaluate` 側の `AnswerInput` の zod で長さと列挙は検証されますが、`evidence: "external"`（外部確認。ベンダー回答より強い根拠）や、依頼と違う資産・緩和策への回答は通ります。また `choiceMap: []` でも項目は読み込まれ、`recordReply` は `AlreadyAnsweredError` を返し続けます。
- 悪用の条件：`.data/requests.json` を書き換えられる人（同じ PC の別の利用者、BR-008）。手元のファイルなので「条件が厳しい」として低。まとめ依頼で親子の整合を読み込みで見るときに、同じ場所で `answer` も見るのが自然です（SBR-014）。
- 直し方の案：`StoredShape` に `answer` の形（`choice` が `choiceMap` の `id` にある、`input.assetId`・`mitigation` が項目と同じ、`evidence: "vendor"`）を足し、合わなければ `answer` だけ捨てて警告を出す。
- 規模：小。

### BR-006（低）テンプレートの書き手では、依頼の作成（SMTP の送信）に 1 分あたりの上限が無い

- 該当：`routes/requests.ts:135`（`takeClaudeSlot` は Claude を呼ぶときだけ）、`mail/mailer.ts:43-75`
- 何が起きるか：`SMTP_URL` を設定した環境で、書き手を `template` にした要求は回数の上限に当たらず、`maxRequests`（1,000。BR-001 の穴もある）まで、1 要求 1 通で送れます。手元の画面からだけなので、影響は利用者自身のアドレスからの大量送信（送信元の信用）です。まとめ依頼は常にテンプレートなので、この穴をそのまま引き継ぎます（SBR-012）。
- 直し方の案：`limits.ts` に `mail` の窓（例：10 通／分）を足し、`SmtpMailer` の `send` の直前で取る。送信箱だけ（`OutboxMailer`）のときは数えない。
- 規模：小。

### BR-007（情報）`question.choices` と `choiceMap` を別々に保存し、読み込みで対応を検査していない

- 該当：`store/requests.ts:53-71`、`routes/requests.ts:167-181`
- 作るときは同じ `q.choices` から両方を作るので対応は保たれています（`questions.ts` の並び順 → `numberedChoices` → 本文の番号 → `question.choices` → 送信箱の番号、が 1 本の並びであることをコードで確認）。読み込みでは、長さと `id` の並びが同じかを見ていません。ファイルの書き換え以外では崩れないので情報扱いですが、SBR-008 の検査を読み込みにも置くと、1 問の依頼でも守れます。

### BR-008（情報）`.data/requests.json` は既定の権限で作られ、同じ PC の他の利用者から読める

- 該当：`store/requests.ts:137-143`（`mkdirSync`、`writeFileSync` に `mode` 無し）
- 宛先のメールアドレス、会社名、資産名、依頼文、回答が入るファイルです。利用者の umask が `022` なら `0644` で、同じ PC の別の OS アカウントから読めます。まとめ依頼で 1 件の情報量が増えるので、`mkdirSync(dir, { recursive: true, mode: 0o700 })` と `writeFileSync(tmp, …, { mode: 0o600 })` を勧めます（Windows では無視されます）。Docker は `USER node` で単一利用者なので影響しません。

### 案から変えた点の評価

- **保存の枠の予約と `addBatch` の見直し**：予約は同期で、`store.size + reserved + n > max` を見てから `reserved` を増やし、`finally` で戻します。例外（`send` が投げる、`takeMailSlot` の 429）でも戻ることを探りの試験で確かめました。上限を超える要求はメールを送る前に 429 になるので、案より安全です。
- **`GET /api/requests` が `items` と `batches` を返す形**：子は `parentId` つきで `items` に残るので、古い画面（`batches` を知らない）でも子が単独の依頼に見えるだけで壊れません。`batches` には本文と宛先が入りますが、`items` と同じ情報です。
- **プレビューの宛先なしの許可**：作成は宛先が無ければ 400 で、画面は `looksLikeEmail` が通るまで「積む」を押せません。プレビューは保存も送信もしないので、宛先なしを許しても攻撃面は増えません。
- **`expectText` による文面の一致**：本文だけを比べ、宛先と件名は比べません。宛先はプレビューで利用者が直すものなので妥当で、件名は件数と会社名からしか作られないので本文が同じなら同じです。ただし省略できるので、API を直接叩く経路では確認を飛ばせます（AR-002）。
- **`requestRoutes` の `onError` と、既存試験の `500→400`**：`app.ts:87-96` は前から zod の例外を 400 にしていたので、アプリ全体の挙動は変わっていません。変わったのは `requestRoutes` を素の `Hono` に載せて単独で動かす試験（`requests.test.ts:91-94`）で、以前は経路に `onError` が無く 500 だったものが 400 になった、という期待値の修正です。後退ではなく、経路単独でも内部情報を出さない方向です。`HTTPException` は経路の `onError` では扱いませんが、`bodyLimit` などの `HTTPException` を投げる middleware はアプリ側に掛かるので、`app.onError` が受けます。

### 新しく見つけた問題（AR）

#### AR-001（低）`deadline` を無害化していない

- 該当：`apps/web/src/server/routes/requests.ts:283`（`body.deadline ?? defaultDeadline(now())`）、`packages/llm/src/writer.ts:224`（`ご回答の期限：${i.deadline}`）。1 項目 1 依頼（`:191`）と対策依頼文も同じ
- 何が起きるか：`deadline` は 40 字までの任意の文字列で、`sanitizeName` を通りません。`"x\n■ 質問 3／2\n偽の質問" + U+202E` を渡すと、本文の末尾に偽の質問の見出しと双方向制御文字が素のまま入りました（確認済み。`requests-batch-post.security.test.ts` の `it.fails`）。
- 悪用の条件：API を直接叩く必要があります。画面は `deadline` をサーバのプレビューの値からそのまま返すだけで、利用者が入力する欄はありません。他サイトからは SEC-002 で止まります。
- 直し方の案：`prepareBatch` と `POST /` で `deadline` に `sanitizeName` を通し、改行も取り除く（または `/^[0-9０-９年月日\s()（）〜-]+$/` のような形に限る）。
- 規模：小（2 行）。

#### AR-002（低）`expectText` が任意なので、API 直接なら「見た文面と送る文面の一致」を飛ばせる

- 該当：`apps/web/src/shared/requests.ts:179`（`expectText: ... .optional()`）、`routes/requests.ts:323`
- 何が起きるか：`expectText` を省いた `POST /batch` は 201 で積まれ、送られます（確認済み）。画面は必ず渡しますが、SBR-016 の守りがサーバ側では任意になっています。
- 直し方の案：`POST /batch` では `expectText` を必須にする（`z.string().max(60_000)`）。試験の `batch()` の補助関数はプレビューを先に取る形に直す。
- 規模：小。

#### AR-003（情報）送れなかった SMTP 送信も通数に数える。窓は 60 秒のスライド

- 該当：`routes/requests.ts:214, 331`（`takeMailSlot` は `send` の前）
- 失敗した送信も 1 通と数えるので、SMTP が落ちているときは 10 回で 429 になります。安全側の振る舞いで、問題ではありません。プレビューは数えません（確認済み）。

#### AR-004（情報）作成の最中に「送信箱を空にする」を押すと、作成中の依頼はそのあと積まれる

- 該当：`routes/requests.ts:328-385`（`send` の `await` の間に `DELETE /` が入る）
- `cleared: 0` が返ったあとに 201 で 3 件積まれます（確認済み）。利用者の操作の順序の問題で、害はありません。

#### AR-005（情報）保存ファイルに同じ id の親が 2 つあれば、後のものが勝つ

- 該当：`store/requests.ts:184-188`
- 本文を書き換えた複製を後ろに置くと、その本文で読み込まれます。`childIds` は実際の子から作り直されるので親子は壊れません。ファイルを書き換えられる人（同じ PC の別の利用者。0600 で読めなくした）だけが条件なので、情報扱いです。

#### AR-006（情報）親の削除で、回答済みの子の数だけ `retract` が流れる

- 該当：`store/requests.ts:502-525`、`client/hooks/useRequests.tsx:122-126`
- 10 問すべて回答済みの親を消すと `retract` が 10 件流れ（確認済み）、別のタブは件数ぶん `refresh()`（`GET /`）を呼びます。上限は 10 なので可用性の問題にはなりません。

#### AR-007（情報）500 の応答に、Mailer が投げた例外の文が出る

- 該当：`routes/requests.ts:143-144`（`publicMessage`）
- `send` が `Error("/Users/.../secret: boom")` を投げると、応答は `[パス] boom` のようにパスを伏せた文になります（確認済み）。`SmtpMailer` は例外を捕まえて `sendError` にするので、実際にこの経路に来るのは差し替えの Mailer だけです。
