# 架空の会社のカルテ（examples/）

ここにある会社はすべて架空です。会社名、人物、数値、ドメイン（`*.example`）に実在のものはありません。
`GET /api/examples` が一覧を、`GET /api/examples/:id` が各カルテを `CompanyProfile`（`packages/engine/src/types.ts`）で検証して返します。画面では上部バーの会社のチップから選べます。

3 社は、同じ事例を当てたときに結論が分かれるように設計しています。結論は `packages/engine` の判定ルール（`knowledge/rules/*.yaml`）と型紙（`knowledge/templates/*.yaml`）で決まり、カルテ側の対策の有無だけで作っています（ルールと型紙は変えていません）。

## 3 社 × 事例 1・2・5 の結論

事例は `eval/recordings/ipa-case-{1,2,5}.with-knowledge.json`（IPA 事例集の読解結果の記録）。表の結論は `evaluate()` を実際に通して確かめた値です（2026-11-03）。

| 会社                                                | 事例 1：VPN からの業務停止（ransomware）                                                                                                        | 事例 2：クラウドストレージの設定ミス（data_breach）                   | 事例 5：社長のメール乗っ取りによる送金詐欺（bec）                                                 |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| デモ精工株式会社（製造業・120 名）                  | **breached** 大丈夫ではない。受注・生産管理が 10 日止まる。取引先担当者の連絡先 3,000 件 → 報告義務あり                                         | **blocked** 止められる（公開リンクの禁止と棚卸しあり）                | **breached** 大丈夫ではない。社長だけ多要素認証の例外、折り返し確認の手順なし → 約 500 万円の流出 |
| デモ物産株式会社（卸売・サービス、事務所型・60 名） | **no_entry** この攻撃の入口はない（VPN 装置なし、中核はクラウド）                                                                               | **breached** 大丈夫ではない。取引先リスト 8,000 件 → 報告義務あり     | **blocked** 止められる（社長を含む全員に多要素認証）                                              |
| 医療法人デモ会 デモクリニック（医療・福祉・40 名）  | **mitigated** 侵入は防げないが被害は抑えられる。受付・診療・検査・処方・会計の 4 業務が 3 日で復旧。診療記録 12,000 件（要配慮） → 報告義務あり | **no_entry** この攻撃の入口はない（クラウドストレージを使っていない） | **pending** 確認中（院長のアカウントの多要素認証の例外と、送金の手順が未確認）                    |

## 会社ごとの設定と根拠

### デモ精工株式会社（`demo-seiko.json`、`pattern: manufacturing`）

| 項目               | 設定                                                                                       | 結論への効き方                              |
| ------------------ | ------------------------------------------------------------------------------------------ | ------------------------------------------- |
| VPN 装置           | 公開、悪用確認済みの脆弱性に該当（`knownExploited: true`）、更新の運用なし（M1051 absent） | 事例 1 の入口が突破される                   |
| 管理者アカウント   | 分離と EDR が未確認（M1026 / M1040 unknown）                                               | 事例 1 は未確認を最悪の想定で進める         |
| 業務サーバ区画     | 分離なし（M1030 absent）                                                                   | 横展開が突破される                          |
| バックアップ       | クラウド同期のみ、切り離しなし、復旧テスト未実施                                           | 復旧できない → 受注・生産管理が 10 日止まる |
| クラウドストレージ | 公開リンクの禁止（M1022 present）、四半期の棚卸し（M1047 present）                         | 事例 2 が止まる                             |
| 社長のメール       | 多要素認証の例外（`mfaException: true`）                                                   | 事例 5 の乗っ取りが突破される               |
| 経理担当           | 研修のみ（M1017 present）、折り返し確認の手順なし（UD-01 absent）                          | 人次第 → 送金される                         |

### デモ物産株式会社（`demo-bussan.json`、`pattern: office`）

| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 社外からの接続               | VPN 装置なし、保守接続なし（`remoteAccess: cloud_only`）                                                                | 事例 1 の型紙の入口（VPN・リモートデスクトップ・保守接続）がない                             |
| 販売管理システム             | クラウド（`side: external`、M1032 present）                                                                             | 社内サーバ区画がなく、社員 PC からも中核へ線がつながらない → 事例 1 は入口なし               |

| 管理者アカウント     | 全 PC で共通（M1026 absent）、EDR なし                                                                                  | 管理者権限が奪われる                                                                   |

| 院長のメール         | **例外になっていないかが未確認（M1032 unknown）**、使い回し防止策も未確認                                               | 事例 5 の乗っ取りが「未確認」になる                                                    |
| 事務長（経理担当）   | 研修なし、折り返し確認の手順が未確認（UD-01 unknown）                                                                   | 人の段階も「未確認」→ 未確認だけなので pending                                         |

## 狙いからの調整（知識ファイルは変えずに、カルテ側で合わせた点）

- **デモクリニックの VPN 装置の更新の運用**：当初の狙いは「更新の運用あり（M1051 present）、該当する悪用確認済み脆弱性なし」で mitigated にすることでした。しかし判定ルール `ransomware.entry.vpn` は、悪用確認済みの脆弱性に該当せず M1051 が present なら入口を **blocked** にします（経路がそこで終わるので結論は「止められます」になり、バックアップの復旧は判定に出ません）。mitigated（侵入は防げないが復旧できる）にするには入口が突破される必要があるので、「ファームウェアは導入時のままで更新の運用は決まっていない（M1051 absent、ベンダー回答）」に変えました。
- **デモクリニックの院長のメール**：当初の狙いは「院長のメールは多要素認証あり、送金の手順は未登録 → pending か人次第」でした。判定ルール `bec.takeover` は、アカウントの M1032 が present なら乗っ取りを **blocked** にして経路が終わるため、送金の手順（UD-01）は判定に出ず、結論は「止められます」になります。そこで、クラウドメール全体には多要素認証を導入済み（M1032 present）としつつ、院長のアカウントが例外になっていないかは未確認（M1032 unknown）としました。乗っ取りと送金の両方が未確認になり、結論は pending（確認中）です。
- デモ物産の事例 1 は、VPN 装置が無いだけでなく中核（販売管理）がクラウドにあることで入口なしになります。社員 PC は型紙の入口候補（フィッシング）ですが、社内サーバ区画が無いため中核まで線がつながらず、入口に数えません。

## 確かめ方

```bash
pnpm knowledge:check
```
